## 1. 왜 이렇게 찍는가

Quantinue MVP-2의 상품 가치는 `감시 → 사건 감지 → 전략 재판단 → critic 검토 →
모의 청산·재배분 → 운영 원장 확인`이 하나의 시스템으로 연결되어 있다는 데
있다. 그런데 실제 시장은 촬영 시간에 맞춰 ±5% 급변이나 중요 뉴스를 만들어
주지 않는다.

그래서 영상은 두 구간으로 나눈다.

| 구간 | 환경 | 화면 표기 | 보여주는 것 |
|---|---|---|---|
| 본편 (5~7분) | 일회용 데모 런타임: 포트 8022 + 일회용 DB + mock 브로커 + 각본 mock LLM | `DEMO / MOCK LLM / MOCK BROKER` | 핵심 흐름을 각본으로 결정론 재현 |
| 실증거 (약 1분) | 운영 8020 + DB 5445, **읽기 전용** | `LIVE OPS (READ-ONLY)` | 실제 Alpaca 감시·OpenAI 사용 원장·heartbeat·Telegram 이력 |

통제 데모와 실제 운영 증거를 화면·내레이션에서 명확히 구분하는 것이 이 영상의
신뢰성 장치다. fixture 결과를 실거래처럼 오인시키지 않는다.

내레이션 원칙 하나를 더 지킨다: **"구현 완료"와 "운영 활성"을 구분해 말한다.**
장중 LLM 재판단(`rejudge`)과 웹소켓 스트림은 구현 완료지만 운영에서는 아직
비활성이며(Gate B 검증 뒤 활성화), 데모 런타임에서만 켜서 시연한다. 이 사실을
숨기지 않는다.

## 2. 본편 장면 구성 (S1~S6, 결정론 등급 순)

| 장면 | 내용 | 재현 방법 | 성격 |
|---|---|---|---|
| S1 | 초기 계좌·보유·일일 판단 결과 훑기 (관제실 `/admin`, 사용자 `/me`) | 데모 DB 시드(계좌+포지션) | 화면 안내 |
| S2 | 가격 급락 → 1분 감시 → 브래킷 손절 → 방어선 내역 카드 | 각본 시세 주입. **LLM 무관 결정론 경로** | 안전장치 |
| S3 | 호재 사건 유입 → 라우팅 → 재판단(전략가+critic) → 표적 매수 | 각본 사건 + 각본 mock(buy). 데모에서만 `rejudge=true` | 상품 가치 |
| S4 | 악재 사건 → 판단 반전 → 모의 매도 | 각본 mock이 티커별 반전(매도) 응답 | 상품 가치 |
| S5 | 같은 각본 재실행 → 중복 주문 0 · 무사건 tick LLM 0콜 | preflight 검증 쿼리를 화면에 그대로 노출 | 운영 규율 |
| S6 | 운영 8020·5445 읽기 전용 실증거 | poll-only 감시 상태, OpenAI 원장, heartbeat, Telegram 이력 | 신뢰성 |

제외한 장면: 웹소켓 스트림 장애 → 폴링 fallback 라이브 재현. 스트림은 실키
PUBLIC 모드에서만 동작해 결정론 재현 비용이 장면 가치를 넘는다. 하이브리드
설계(보유 종목만 스트림 + 나머지 1분 폴링, 30종목 한도 실측)는 내레이션과
관제실 화면으로 설명한다.

## 4. 구현 및 준비 작업

모든 코드 작업은 실패 테스트부터 시작한다. 데모 부품은
`app-v2/src/quantinue/demo/`와 `app-v2/scripts/run_demo.sh`에서만 조립하고,
운영 기본 조립은 데모 패키지를 import하지 않는다.

### 4-1. 각본 시세와 고정 시계

- `LatestTradeSource` 계약을 구현하는 각본 시세 소스를 만든다.
- 티커별 가격열은 `안정 → 손절선 하회 → 안정`처럼 호출 순서에 따라 전진한다.
- 뉴욕 정규장 안의 고정 시각과 기존 `NyseCalendar.is_market_open()`을 사용해
  실제 촬영 시각과 관계없이 WatchRunner가 같은 결과를 낸다.
- 운영 시세 fixture와 기본 factory의 의미는 변경하지 않는다.

완료 기준:

- 같은 시나리오를 두 번 만들면 동일한 가격열이 나온다.
- 시세가 소진되거나 알 수 없는 티커가 들어오면 주문 없이 명시적으로 실패한다.
- 장외·휴일·실제 벽시계에 의존하는 테스트가 없다.

### 4-2. 시나리오 mock LLM

- 기존 고정 mock을 바꾸지 않고 데모 전용 analyzer를 만든다.
- 호재 티커는 `buy`, 악재 티커는 `sell/reversal`, critic은 승인으로 고정한다.
- 알 수 없는 티커는 `hold/no-action`으로 닫아 예상 밖 주문을 금지한다.
- 실제 OpenAI 호출과 비용은 0이지만 데모 DB에는 mock 사용 원장을 남긴다.

완료 기준:

- 같은 입력은 항상 같은 구조화 결과와 원장 행을 만든다.
- S3는 해당 티커만 매수하고 S4는 해당 보유 티커만 매도한다.
- 미등록 티커·잘못된 시나리오는 주문 0건이다.

### 4-3. 각본 사건 소스

- 호재 기사 1건과 악재 기사 1건을 고정 payload로 제공한다.
- 기존 증분 수집·정규화·라우팅·evidence 경로를 그대로 통과시킨다.
- 같은 사건을 다시 넣으면 새 사건·재판단·주문이 생기지 않는다.
- 보유 종목과 당일 후보 밖의 티커는 라우팅 단계에서 제외한다.

완료 기준:

- 첫 수집은 사건별 1회 처리, 재수집은 신규 0건이다.
- `rejudge=false`에서는 저장만 하고 LLM 호출 0건이다.
- 데모의 `rejudge=true`에서는 사건·티커·성향별 정확히 1회 판단한다.

### 4-4. 전용 seed와 일회용 런처

- 데모 포트는 **8022**, 데모 DB 포트는 **5490**으로 고정한다.
- `quantinue.demo.seed` 전용 모듈이 기존 repository와 MockBroker 계약을 사용해
  계좌, 거래 가능 유니버스, 승인 시그널, 브래킷 주문, fill과 시작 포지션을
  생성한다.
- 일일 잡 전체를 먼저 실행하는 방식과 임의의 raw SQL seed를 사용하지 않는다.
- `run_demo.sh start`는 DB 생성·스키마 멱등 적용·seed·앱 기동을 수행한다.
- `reset`은 DB를 버리고 같은 seed로 복원하며, `stop`은 컨테이너·프로세스·
  데모 전용 lock을 제거한다.
- workers와 `rejudge`는 데모 overlay에서만 켠다. 운영
  `config/pipeline.yaml`은 수정하지 않는다.

완료 기준:

- `start → health(8022) → reset → 동일 원장 → stop`을 두 번 반복해 통과한다.
- reset 전후 핵심 행 수와 금액·티커·주문 키가 일치한다.
- 8020이 실행 중이어도 포트·DB·lock 충돌이 없다.
- 5444·5445·5480을 지정하면 연결 전에 nonzero로 거부한다.

### 4-5. 촬영 preflight

촬영 직전에 한 명령으로 다음을 확인한다.

1. 현재 앱이 8022이고 DB가 5490인가
2. mock LLM·MockBroker·workers·rejudge가 데모값인가
3. 중복 idempotency key와 중복 fill이 0건인가
4. 무사건 tick의 LLM 호출이 0건인가
5. 비밀 검사가 통과하는가
6. 8020·5445에 쓰는 명령이 포함되지 않았는가

항목별 실패는 서로 다른 이유와 nonzero 종료 코드로 표시한다.

### 4-6. S1~S6 계약과 dress rehearsal

- 데모 티커, 초기 현금, 보유 수량, 손절·익절선, 가격열, 사건 payload,
  기대 주문·fill·관제 카드 값을 버전된 계약 파일로 고정한다.
- `start → S1~S5 → reset → S1~S5 → stop`을 실행한다.
- 두 실행의 핵심 원장 결과가 동일하고 중복 주문이 0건이어야 한다.
- 장면별 실제 소요 시간을 기록해 총 6~8분 안에 들어오는지 확인한다.

### 4-7. 실제 운영 증거 준비

- 8020·5445에는 GET과 SELECT만 사용한다.
- 실제 poll-only 상태, OpenAI usage 원장, heartbeat, Telegram 이력을
  촬영 전에 가림 처리해 확인한다.
- 항목이 촬영일에 보이지 않을 경우 사용할 정직한 대체 내레이션을 준비한다.
- 토큰, chat ID, 쿠키, heartbeat URL은 화면과 파일에 남기지 않는다.

### 4-8. 스트림 fallback 처리

웹소켓 강제 단절을 라이브 장면으로 만들지는 않는다. 대신 다음 증거를 사용한다.

- 스트림 재연결 중 폴링 지속 테스트 결과
- 스트림과 폴링이 같은 가격을 보아도 청산이 한 번뿐인 테스트 결과
- 관제실의 stream/poll 상태
- 보유 종목 최대 30개 스트림, 나머지 1분 폴링이라는 내레이션

따라서 영상은 fallback 기능을 누락하지 않되, 네트워크 장애를 연출하다 촬영이
불안정해지는 위험은 피한다.

## 5. 금지선 (Must NOT)

- 운영 8020·DB 5445에 **어떤 쓰기도 하지 않는다.** 재기동·수동 OpenAI 호출
  포함 금지. 실증거 구간은 SELECT/GET만.
- 실제 OpenAI로 반복 촬영하지 않는다. 데모 LLM은 각본 mock뿐이다.
- 데모 부품을 운영 기본 경로에 노출하지 않는다 — 주입은 데모 진입점에서만
  (테스트 stub과 같은 방식). 운영 조립 코드는 데모 패키지를 import하지 않는다.
- 실제 브로커 주문 없음. `config/pipeline.yaml` 운영값(±5%·쿨다운 30분·스윕
  3회·예약 20%) 변경 없음 — 각본이 운영값에 맞춘다.
- 데모 런타임에 8020/8021 포트, 5444/5445/5480 DB를 쓰지 않는다. `app/`(1차)
  불가침, push는 사용자 지시 전 금지.
- 토큰·키·Telegram 식별자를 대본·화면·증거 파일에 남기지 않는다.
- 영상 편집 자동화·외부 업로드·사건 전용 탐색 UI 개발은 범위 밖.

## 6. 촬영 성공 기준

- 6~8분 안에 초기 계좌 → 사건 감지 → 재판단 → critic → 모의 주문·체결 →
  재배분 → 관제 원장 확인까지 끊김 없이 이어진다.
- 같은 각본 재실행에서 중복 주문·중복 체결 0건, 무사건 tick LLM 호출 0건을
  화면으로 보여준다.
- DEMO와 LIVE OPS 표기가 전 구간에서 유지되어 시청자가 혼동할 수 없다.
- 운영 8020·5445에 데모 흔적이 전혀 남지 않는다.
- 촬영 실패 시 리셋 → preflight → 동일 결과 재촬영이 가능하다.

## 9. 촬영 당일 체크리스트

### 촬영 전

- 8020과 5445가 정상인지 읽기 전용으로 확인한다.
- `run_demo.sh reset` 후 preflight를 실행한다.
- 브라우저 탭, 확대 비율, 알림, 화면 해상도를 고정한다.
- DEMO와 LIVE OPS 라벨이 각 구간에 표시되는지 확인한다.
- 비밀값과 개인 식별 정보가 화면에 없는지 확인한다.

### 촬영 중

- S1~S5에서는 8022만 사용한다.
- S6에서만 8020을 열고 GET/SELECT 이외 동작을 하지 않는다.
- fixture 결과를 실제 시장 사건이나 실거래라고 표현하지 않는다.
- 구현 완료와 운영 활성 상태를 구분해 말한다.

### 실패한 take 복구

1. 녹화를 중지한다.
2. `run_demo.sh reset`을 실행한다.
3. preflight green을 확인한다.
4. 처음부터 다시 녹화한다.
5. 부분 원장을 손으로 고치거나 이어 찍지 않는다.

### 촬영 후

- `run_demo.sh stop`으로 데모 프로세스·DB·lock을 제거한다.
- 8020 health와 5445 상태가 촬영 전과 같은지 확인한다.
- 녹화본에서 비밀과 DEMO/LIVE 라벨을 다시 확인한다.

## 10. 최종 승인 기준

- 전체 유닛·웹과 데모 테스트가 green이고 Ruff가 clean이다.
- 데모 전체 사이클을 reset 사이에 두 번 실행해 동일 결과를 얻는다.
- 중복 주문·중복 fill 0건, 무사건 LLM 0콜이다.

- 전달 정본만 읽은 사람이 별도 질문 없이 촬영·복구할 수 있다.
- 대본의 모든 주장이 화면 또는 원장 증거와 연결된다.
