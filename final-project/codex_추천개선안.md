# Codex 검증 결과 및 추천 개선안

검증일: 2026-07-28  
검증 대상: `handoff-2026-07-28.md`, `slides/index.html`, 발표 대본·계획·인수인계 문서, 슬라이드 자산·영상·PDF  
원칙: 이 문서만 새로 작성했으며 기존 발표 내용과 파일은 수정하지 않았다.

## 1. 결론

현재 HTML 슬라이드는 **조건부로 발표 가능한 상태**다.

- 검증 중 추가된 투자 페르소나 장까지 포함해, 실제 Chrome에서 최신 19장(본편 17장 + 백업 2장)이 모두 정상 렌더링됐다.
- 이미지 누락, 브라우저 오류, DOM 기준 잘림·넘침은 발견되지 않았다.
- 키보드·클릭 이동, 전체화면, 동영상 재생·자동 일시정지가 정상 작동했다.
- 디자인 체계와 발표 서사는 전반적으로 일관되고 완성도가 높다.

다만 발표 전에 아래 5개는 반드시 확인하는 편이 좋다.

1. **14번 슬라이드의 운용 성과와 SPY 비교 기준일이 서로 다르다.**
2. **13번 슬라이드의 “단계를 지날수록 수가 줄어든다”는 설명이 실제 수치와 맞지 않는다.**
3. **테스트 개수 993건이 최신 인수인계의 804건 기록과 어긋난다.**
4. **`주문 62 = 체결 62`만으로 중복 주문 0건을 증명할 수는 없다.**
5. **`quantinue-final.pdf`가 현재 HTML보다 오래된 16장 버전이다.**

위 항목은 단순한 미관 문제가 아니라 질문을 받았을 때 신뢰도에 직접 영향을 줄 수 있다.

## 2. 발표 전 우선 개선 권고

### P0 — 수치와 비교 기준 바로잡기

#### 2-1. SPY와 운용 성과를 같은 종료일로 맞추기

`slides/index.html` 14번 슬라이드에는 다음 정보가 동시에 들어 있다.

- 레이블: `SPY (같은 기간 · 100 기준)` (`slides/index.html:678`)
- 운용 곡선: 07-28까지 표시
- SPY 곡선: 07-27까지만 표시 (`slides/index.html:687`)
- 주석: `SPY는 07-27 종가까지 적재` (`slides/index.html:694`)
- 표: 양쪽을 `7거래일 수익률`로 비교 (`slides/index.html:698`)

따라서 현재의 `운용 -0.34% vs SPY -0.44%`는 엄밀히 말해 같은 기간 비교가 아니다.

권고안은 둘 중 하나다.

- SPY 데이터를 07-28까지 적재한 뒤 두 수익률을 다시 계산한다.
- 또는 운용 곡선도 07-27에서 잘라 같은 종료일 기준으로 다시 계산한다.

두 기준이 맞기 전에는 “같은 기간” 또는 상대 초과성과로 해석될 표현을 사용하지 않는 것이 안전하다.

#### 2-2. 13번 슬라이드의 퍼널 논리를 실제 단위에 맞추기

현재 문장은 `단계를 지날수록 수가 줄어듭니다`인데 실제 표시는 `222 → 342 → 323`이다 (`slides/index.html:650-656`).

이는 후보 종목과 AI 판단 건수의 단위가 다르고, 후보 하나를 두 페르소나가 판단할 수 있어 AI 판단 건수가 후보보다 커지는 구조이기 때문이다. 현재 그래프는 퍼널이라기보다 **분기 후 재집계**에 가깝다.

권고안:

- 제목은 `2,000개 종목에서 62건이 체결되기까지`처럼 출발 집합과 결과 이벤트를 문법적으로 분리한다.
- “후보 → 두 페르소나 판단 → 규칙 통과”처럼 단위가 바뀐다는 점을 제목과 설명에 명시한다.
- 단조 감소를 전제로 한 “퍼널” 표현 대신 분기형 흐름도나 단계별 집계로 표현한다.
- 퍼널을 유지하려면 동일한 모수의 통과율만 비교하도록 수치를 다시 구성한다.

#### 2-3. 최신 커밋에서 테스트 개수를 다시 확정하기

슬라이드는 `993 = 유닛·웹 803 + 통합 190`으로 표시한다 (`slides/index.html:663`). 반면 최신 인수인계에는 배분 버그 회귀 테스트가 추가된 뒤 `유닛·웹 804`로 기록돼 있다.

단순히 993을 994로 바꾸기보다는 최신 상태에서 다음 두 묶음을 모두 다시 실행한 뒤 확정하는 것이 맞다.

- 유닛·웹 테스트
- 통합 테스트

통합 190건이 최신 커밋에서도 그대로 통과했는지 확인된 뒤 합계를 반영해야 한다.

#### 2-4. `주문 62 = 체결 62`가 증명하는 범위를 좁히기

13번 슬라이드는 주문 수와 체결 수가 같다는 사실을 `같은 주문을 두 번 낸 적이 없습니다`의 근거로 사용한다 (`slides/index.html:657`). 그러나 두 수가 같다는 것만으로는 중복 주문이 없었다는 결론이 나오지 않는다. 중복 주문도 체결되면 주문과 체결 수는 같을 수 있다.

이 수치가 직접 말해 주는 것은 “미체결·거절 없이 기록된 주문이 모두 체결됐다”에 가깝다. 중복 주문 0건을 주장하려면 다음 중 실제로 구현·검증된 근거를 함께 제시하는 편이 좋다.

- 주문 idempotency key 또는 고유 제약
- 동일 신호·계좌·종목·시각대의 중복 탐지 쿼리 결과
- 재시작 회귀 테스트와 해당 테스트 이름

### P0 — 발표 백업 파일 최신화

현재 `slides/quantinue-final.pdf`는 16페이지이며, 최종 HTML은 19장이다. 파일 수정 시각도 PDF가 HTML보다 약 6시간 이르다.

검증 과정에서 현재 HTML을 인쇄한 결과는 정상적으로 19페이지 PDF가 생성됐다. 즉 인쇄 CSS 자체는 작동하며, 저장된 PDF만 오래된 상태다.

권고안:

- 위 수치 수정이 끝난 뒤 PDF를 다시 생성한다.
- 재생성 전까지는 기존 PDF를 “최종 백업”으로 사용하지 않는다.
- 새 PDF의 페이지 수가 19장인지, 영상 슬라이드가 의도한 정지 화면으로 보이는지 확인한다.

나머지 문서에는 “과거 계획/보관용” 표시를 붙이거나 상단에서 최신 문서로 연결하는 것을 권한다.

### P1 — 비율의 분모와 측정 기간 표시

8번 슬라이드의 `게이트 84% / LLM 16%`와 `비평가 반려 18%`는 서로 다른 분모의 지표지만 가까이 배치돼 있어 16%와 18%가 모순처럼 보일 수 있다. 각각 “전체 후보 중 AI 비평가로 간 비중”과 “비평가 검토 323건 중 반려 57건”처럼 분모를 붙이는 것이 좋다.

13번 슬라이드도 전체 기록은 7거래일인데 AI 비용은 4일간 `$0.53`이다. 값 자체보다 측정 창이 다르다는 점이 보이도록 `비용 계측 4일`을 더 분명히 표시하면 질문을 줄일 수 있다.

### P1 — 발표자 변경 시 백업 답변도 함께 확인

`to_jihyun.md`는 발표자가 바뀌면 대본의 3번 슬라이드 문단만 수정하면 된다고 안내한다. 그러나 백업 1번 슬라이드에는 `본인은 뭘 했나요?`라는 질문과 문성혁 개인 기준의 답변이 들어 있다 (`slides/index.html:759`).

발표자가 문성혁이 아니라면 다음 두 곳을 함께 확인해야 한다.

- 본편 3번 슬라이드의 담당 범위
- 백업 1번 슬라이드의 개인 기여 답변

또한 백업 답변의 `2차는 전체를 인수받아`라는 표현은 기존 문서에 기록된 “과도한 주장처럼 들리지 않게 조정”하려는 방향과 어긋날 수 있으므로 최종 어조를 한 번 확인하는 것이 좋다.

### P1 — 실제 발표 노트북에서 폰트와 이모지 확인

슬라이드는 `Apple SD Gothic Neo`와 설치형 `Pretendard`에 의존하며 웹폰트를 포함하지 않는다 (`slides/index.html:29`). Mac이 아니거나 Pretendard가 없는 PC에서는 글꼴 폭이 달라져 특히 정보가 많은 백업 슬라이드가 다시 줄바꿈될 수 있다.

또한 아키텍처 슬라이드의 이모지는 운영체제마다 모양과 폭이 다르다. 가능하면 향후에는 SVG나 단색 아이콘으로 고정하는 것이 더 안정적이다.

최소 조치:

- 실제 발표 노트북에서 19장 전체를 한 번 넘겨 본다.
- 6번 아키텍처와 18·19번 백업 슬라이드의 줄바꿈을 집중 확인한다.
- HDMI 연결 후 전체화면 비율과 하단 페이지 표시가 잘리는지 확인한다.

성과 그래프의 `5계좌 합산`과 백업의 `운용 6계좌`도 질문을 부를 수 있다. 현재 문맥상 일시정지된 1계좌를 성과 합산에서 제외한 것으로 읽히지만, 이 관계를 발표자 메모에서 명확히 해 두는 편이 안전하다 (`slides/index.html:677`, `slides/index.html:756`).

### P2 — 프로젝터 거리에서의 가독성 다듬기

1600×900 원본에서는 잘림이나 한글 글리프 문제가 없었다. 다만 1280×720으로 축소하면 하단 원장·보조 설명은 실질적으로 13~14px 정도로 보이고, 백업 두 장의 8행 표는 발표장 뒤쪽에서 읽기 빠듯할 수 있다. 보조 글자색 `#6B7C90`과 배경 `#EDF1F6`의 대비도 약 3.77:1이라 작은 일반 텍스트 기준 4.5:1에는 못 미친다.

눈에 띄는 어절 분리도 몇 곳 있다. 예를 들면 2번의 `보유 / 종목`, 8번의 `수 / 있게`, 12번의 `잠가 / 두었습니다`, 15번의 `붙여 / 보니`, 백업의 `착수만 / 보류했습니다`다. 글자 크기를 더 줄이기보다 문장을 짧게 하거나 의미 단위에 줄바꿈 방지를 적용하는 편이 좋다.

또한 4번과 11번의 증거 캡처는 화면 전체 맥락은 보여 주지만 내부 작은 글자는 프로젝터에서 읽기 어렵다. 실제로 읽혀야 하는 필드만 확대 콜아웃으로 보강하면 “증거 화면”의 효용이 더 커진다.

### P1 — 실제 시간으로 한 차례 완주 리허설

영상은 2분 14.3초이며 오디오 트랙이 없다. 대본의 라이브 내레이션과 함께 사용할 의도에는 맞지만, 무음임을 발표자가 알고 있어야 한다.

리허설 체크:

- 12분 30초 목표로 본편 17장을 끝까지 진행
- 영상 슬라이드에서 8개 내레이션 문장의 타이밍 확인
- 영상 종료 후 다음 슬라이드로 넘어갈 때 자동 일시정지 확인
- `F`, 좌우 화살표, `End`, 클릭 이동을 실제 리모컨/키보드로 확인
- PDF 백업은 재생성된 19장 버전만 준비

## 4. 유지할 강점

다음 요소는 현재 상태를 유지하는 것이 좋다.

- 결정론 영역은 초록, AI 판단 영역은 보라, 경고는 황토색으로 구분한 색 체계
- 모든 슬라이드 하단의 원장·증거 좌표 표기
- “AI가 선택하지만 규칙이 검증하고 비판하며 보호한다”는 일관된 서사
- 실제 텔레그램·헬스체크 화면을 사용한 운영 증거
- 새 9번의 방법론·정책 수치가 실제 두 프롬프트와 `app-v2/config/pipeline.yaml`에 일치하고, 대본의 오른쪽 화면 설명도 현재 화면과 일치하는 점
- 과도한 애니메이션 없이 220ms 전환만 사용하고 `prefers-reduced-motion`을 존중한 점
- 백업 슬라이드에 예상 질문과 운영 한계를 숨기지 않고 정리한 점
- 고정 16:9 무대와 전체화면 모드의 안정적인 동작

## 5. 실제 검증 결과

- Chrome에서 본편 17장 + 백업 2장, 총 19장 확인
- 375×667, 768×1024, 1280×720, 1600×900의 4개 뷰포트에서 총 76개 화면 캡처 확인
- 깨진 이미지 0건
- 페이지 스크립트 오류 0건

- 새 9번 제목은 DOM 글꼴 메트릭상 높이가 3px 크게 잡히지만 현재 Mac Chrome 화면에서는 글자 잘림이 보이지 않음. 다른 OS 글꼴 확인 항목에 포함
- 세로 화면에서는 16:9 무대가 레터박스 형태로 축소되며, 발표용 가로 화면에서는 정상 확대됨
